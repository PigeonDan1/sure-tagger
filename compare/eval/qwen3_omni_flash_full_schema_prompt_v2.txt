I. Evidence and conservative rules
1. Do not use the filename, path, dataset priors, outside knowledge, an existing caption,
   reference transcript, or unprovided labels. You may recognize speech internally, but do not fill
   unclear words with a plausible guess based on common knowledge.
2. Fill `duration_sec`, `sample_rate_hz`, and `channels` only when the audio part explicitly exposes
   metadata that you can reliably read; otherwise use null. Never estimate sample rate or channel
   count from listening.
3. SNR, DNSMOS, RT60, and C50 require an instrument or measurement model. Use null when no such
   measurement is provided; do not turn "sounds clear" or "sounds reverberant" into invented numbers.
   Fill `nonspeech_ratio` only when the whole-clip proportion can be estimated reliably, and fill
   `silence_segments` only when timestamps can be determined reliably.
4. `speaker.asr_transcript` must contain only speech that is actually intelligible. Use null when
   there is no recognizable speech; do not use `[inaudible]`, ellipses, or explanatory placeholders.
   Use null for word_count, punctuation, repetition, or filler when they cannot be reliably derived;
   do not count them by impression.
5. Separate speaker analysis from transcript analysis: replay the whole clip for distinguishable
   voices, turn changes, and overlap before filling speaker_count, speaker_change_count,
   overlap_ratio, and profiles. A transcript is one chronological string and does not imply one
   speaker; never choose one speaker merely because the transcript has no speaker IDs. If the number
   of speakers cannot be distinguished reliably, set speaker_count and its dependent fields to null
   instead of representing the most prominent speaker as everyone.
6. Structural fields may be direct listening judgments or explicit rule results. Descriptive fields
   may state directly audible facts or conservative combinations of populated structural fields.
   Do not state a location, room type, device model, occupation or organization, age, identity,
   emotion, accent, ethnicity, microphone distance, stereo position, or instrument model as fact.
   The structured `gender` field in each `speaker_descriptions` item is the only place for a speaker
   gender label; use exactly `male`, `female`, or null, and use null when it is not sufficiently
   supported by the audio. Do not repeat gender in free-text descriptions or phrases. Put necessary
   speculation only in `scene_hypotheses`, using wording such as "possibly" or "more like" and
   lowering confidence.
7. `speaker.profiles` may describe only each distinguishable speaker's relative speech rate, pitch,
   volume, and stability. Never infer gender, age, identity, or health from pitch, timbre, or language.
   Number speakers by the time each speaker first starts speaking (the earliest audible speaking
   onset), in ascending order, as `speaker_1`, `speaker_2`, etc.; do not use model detection order,
   file order, or internal cluster labels, and do not create an identity that cannot be heard. Use
   this same chronological order for `speaker.profiles` and `descriptive.speaker_descriptions`.
   The profile count must match a known speaker_count; if speakers cannot be aligned reliably, set
   profiles to null as a whole. The structured `gender` values in `speaker_descriptions` form the
   evaluated `speaker.gender` sequence in this same order; each value must be exactly `male`,
   `female`, or null.
8. `speech_rate.value` is a real per-speaker speech rate, not a confidence score or arbitrary decimal.
   Fill value and unit only when the distinguishable speaker's words/characters and active speaking
   time support a reliable calculation; otherwise set both to null and retain only an audibly
   supported band. Never use placeholder numbers such as 1.234567.
9. Event enums must use only the schema values. `speech_music_events` must be unique and ordered
   speech, singing, music. `external_noise_type` may contain only music, animal, mechanical, nature,
   formless, and channel_environment, without duplicates. `noise_composition` must retain all six
   keys, each with a string array.
10. `language_content.language` may contain only ar, zh, en, es, fr, hi, ja, ko, ru, sw, or the
    schema-allowed zh-<region> form. Use null for unknown, mixed, or non-normalizable language;
    never substitute a non-language label.
11. Every number must be finite; counts must be non-negative integers; ratios must be in [0,1].
    Use null for invalid or unsupported values. Do not clamp, truncate, or invent values.
    `speech_rate.value` may be non-null only when `unit` is non-null.
12. Compute a deterministic derived field only from known valid dependencies, rounded to six decimal
    places: speaker_change_rate_per_min = speaker_change_count * 60 / duration_sec when duration_sec

    deterministic_derived value independently.
13. After listening, check internally that every key is present; null and [] have the right meaning;
    counts, booleans, events, profiles, descriptions, and topic do not contradict each other. Do not
    output this checking process.

II. Rules for null, [], and descriptive objects
- `null` means unknown, insufficient evidence, not assessable, or not applicable.
- `[]` means that no reportable items are confirmed. For example, use `silence_segments=[]` only
  when no nonspeech interval is confirmed, and `descriptive_phrases=[]` when no reliable phrase is
  reportable. Use null when you cannot tell whether an item exists.
- `facets` and `scene_hypotheses` are optional as well. For these two fields, `[]` is valid when no
  distinct, defensible item is reportable. Do not add an item merely to avoid an empty array, but do
  not use `[]` merely because a specific venue, device, or other fine-grained scene detail is unknown.
- In this audio-only request, `evidence_tags` in `descriptive.facets`, `speaker_descriptions`, and
  `scene_hypotheses` must always be []. Do not invent an `audio` path.
- For these audio-only descriptive objects, `evidence_tags=[]` means that no structural path is being
  cited; it does not by itself mean that the supported item must be removed.
- Every confidence must be a finite number in [0,1]. It is a self-assessment, not a calibrated
  probability. Direct, stable observations may be high; weak combinations and hypotheses should be
  lower. Remove an unsupported array item or use null.
- Write concise, objective Chinese by default even when the speech is in another language. Keep JSON
  keys, enums, speaker IDs, evidence paths, and `facets[].name` in English; facet names use lowercase
  snake_case.
- `caption` is a one-to-three-sentence summary covering the dominant content, salient background
  sounds, overall recording impression, and speaker interaction. Do not mechanically list fields or
  numbers, and do not state a hypothesis as fact. `topic` must be supported by intelligible speech;
  use null when speech content is insufficient. Use at most 3 scene_hypotheses, at most 6 facets,
  and at most one speaker_description per distinguishable speaker.
- `background_condition` summarizes quietness, persistent/intermittent interference, or nonspeech
  conditions. `dominant_content_impression` describes which of speech, music, singing, noise,
  silence, or mixed content dominates; it must not describe emotion, tone, or topic.
  `clarity_intelligibility_impression` describes actual clarity and intelligibility.
  `background_sound_summary` summarizes only sounds actually heard and must not infer a source from
  the topic.
- `descriptive_phrases` and speaker-level descriptive_phrases must be short labels such as
  "alternating speakers", "quiet background", or "fast speech"; never copy transcript sentences,
  quotations, or complete assertions.
- Create facets only for useful, non-redundant dimensions supported by the populated fields. When
  applicable, combine existing observations into a higher-level facet: speaker count/change/overlap
  can support `interaction_pattern`; speech rate, pitch, volume, filler, or repetition can support
  `delivery_style`; speech/music/noise and background condition can support `soundscape`; transcript,
  topic, or dominant content can support `content_impression`; clarity or audible interference can
  support `recording_impression`. These are optional candidates, not mandatory outputs.
- Keep `scene_hypotheses` explicitly hypothetical. When supported, prefer broad interaction-form or
  acoustic hypotheses such as possible monologue, dialogue, group discussion, or speech with a
  background event. Do not infer a specific venue, device, occupation, organization, relationship,
  or other unsupported scene detail. It is valid to return `[]` when no such hypothesis is defensible.
- Do not put gender, age, identity, emotion, or accent in the free-text fields of speaker_descriptions.
  Put gender only in its structured field. Use usability_notes
  only for downstream-use advice. Use uncertainties only for boundaries actually present in this
  audio, not generic disclaimers.
